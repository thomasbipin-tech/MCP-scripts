## Route an office end to end From an empty VLAN list to a generated config: VLANs, SVI gateways with first-hop redundancy, the default toward the firewall and its return path, reaching the other offices, then validate and generate. Relevant for: Professional Services NetOps / Operations Six steps on an office you have already drawn: two Catalyst cores, four access switches, a firewall pair and two SD-WAN appliances, cabled and named. It starts at an empty VLAN list and ends at a configuration you can read line by line. Budget about forty minutes the first time. It does not teach the canvas or the property tabs - it links to them as it goes. 

## Before you start # A drawn office Devices placed, cabled and named. Every hostname, filename and generated stanza keys off the device name, so rename before you configure, not after - The Canvas . One address block A /21 or /22 for the site. Carve it by hand as you go, or let pools do it - IPAM . The firewall address The address on the firewall's inside interface. Decide it before step 4, because the default route names it. Who holds the gateways The core pair, or the access switches themselves. Step 3 settles it - the answer changes what you have to switch on first. Or skip all of it Building a new site rather than extending one? The Blueprint wizard generates every step below, addressed and validated. 

## Step 1 - Define the VLANs # Where to find it Canvas → Select a switch → L2 tab → VLANs → + Add VLAN Each row is an id, a name, an optional purpose and a state. + Add VLAN proposes the next free id. Save to database promotes the row to the project's VLAN database, so the next switch picks it from a list instead of you retyping it, and the two cannot disagree about what VLAN 20 is called. Important The SVI checkbox on a VLAN row is a note to yourself, not an instruction. Nothing reads it: it never reaches the configuration generator, and adding a real SVI in the L3 tab does not tick it. The gateway is created in step 3. A VLAN with the box ticked and no SVI is a VLAN with no gateway. Full field reference, including the VLAN database and bulk editing: Layer 2 . 

## Step 2 - Trunk them, and land the ports # Where to find it Canvas → Select a switch → L2 tab → Switchports Put the new ids on the allowed list of every uplink between the access layer and the cores, and set the access (and voice) VLAN on the user ports. On a pair of cores, the peer link carries them too. Note A missing id on one trunk is the most common reason a gateway that looks perfect does not answer: the SVI is up on the core and the VLAN never reaches it. Validation does not read trunk allowed lists. When the project has a VLAN database, it warns about an access, voice or native VLAN, or an SVI, whose VLAN is in neither the switch's list nor the database. An id left off a trunk is silent, so check the allowed lists by hand. 

## Step 3 - Give each VLAN a gateway # Where to find it Canvas → Select the core switch → L3 tab → SVIs (VLAN Interfaces) → + Add One row per VLAN: VLAN , IP Address , Prefix , a description, and first-hop redundancy where a pair shares the gateway. A new row pre-fills the VLAN from this device's first L2 row. Important The VLAN field is a free number, not a picker. An SVI on a VLAN this switch does not have is accepted, saved, and generates an interface into a broadcast domain that is not there - typing 110 for 10 costs you an afternoon. Check the number against the L2 tab before you leave the row. 

## Auto-assign the group in one click # Address the first switch's row - an IP and a prefix, and the row grows an ⚡ Auto-assign group IPs (VIP + members) button. It takes the subnet from the first switch, in hostname order, that already has an address and a prefix on that VLAN, then numbers every switch in the design that has an SVI on it. No pool and no site are required. Scope Every device in the project with an SVI on that VLAN id, across every canvas tab, not just the site you are looking at. Two sites that both use VLAN 10 are one group, and the second site gets numbered out of the first site’s subnet. Order Members sorted by hostname, ascending from the first usable address. A member that already holds a valid address inside the subnet is left alone; a network or broadcast address is not valid and gets replaced. The VIP The first usable address, with HSRP or VRRP to match the platform and the group number derived from the VLAN id. Written only when at least two members are L3 switches. Not written No IPAM allocation rows. The addresses land on the devices; the pool ledger does not learn about them, so a later auto-assign from the drawer can hand the same space out twice. Important An access switch is not counted as an L3 switch here, so a pair of routed access switches gets member addresses and no virtual IP - the very address the DHCP scope points at is the one not created. Set the first-hop redundancy by hand on both SVIs, or keep the gateways on the cores. Why The first usable address is a convention worth keeping mechanically: the DHCP scope, the firewall's return route and every static anyone writes later all assume the gateway is .1 . A group numbered by hand drifts from that the first time somebody racks another switch, and nothing catches it - the design is still valid, just wrong. HSRP/VRRP fields, secondary addresses, DHCP helpers and the per-platform CLI: Layer 3 . 

## When the gateway lives on the access switch # Open the L3 tab of an access switch and there are no sections - just a card: This access switch is Layer 2 by default. The hardware routes - enable Layer 3 to use it as the LAN gateway (SVIs with HSRP/VRRP, static routes, OSPF/EIGRP/BGP). Press Enable Layer 3 routing and the whole tab appears, with a persistent Layer 3 routing (routed access switch) toggle at the top. Turning it back off keeps what you typed rather than deleting it. Important Everything Layer 3 on that switch hangs off this one switch: ip routing , the SVIs, VRFs, loopbacks, OSPF, EIGRP, BGP and the static routes . Configure the tab with the toggle off and none of it renders. The generator says so, but it says so in the device's Config tab and in the Generate drawer, which report what the template did. It does not appear in Validate , which checks the design and never sees the template. Why The opt-in exists so a closet switch does not grow a routing table by accident - an OSPF adjacency where nobody wanted one is harder to find than a missing gateway. The price of that choice is exactly this warning, which is why it matters that you know which drawer prints it. 

## Step 4 - Point the office at the firewall, and the firewall back at the office # Where to find it Canvas → Select the core switch → L3 tab → Static Routes → + Add A default route toward the firewall is 0.0.0.0 / 0.0.0.0 with the firewall's inside address as the next hop. Metric / AD makes a second route a floating backup, and IP SLA tracking (failover) withdraws the route when a probe stops answering. Important The 0.0.0.0 you can see in Prefix and Mask is placeholder text, not a value - type it into both. A blank mask renders as 255.255.255.0 , giving you a /24 whose description claims it is the default route. A blank prefix or next hop drops the route from the configuration entirely. A default is only half of it. An office core carries three routes, and the third one lives on the other box: 0.0.0.0/0 → firewall Internet-bound traffic, inspected on the way out. supernet → WAN edge The corporate supernet (say 10.0.0.0/8 ) toward the SD-WAN appliance. Longer than the default, so it wins on prefix length and only Internet traffic takes the firewall. Step 5 can replace this one with a routing session. inside subnets → core On the firewall itself, a route back for every subnet behind the core. Without it traffic leaves and never returns, and the symptom looks like a firewall rule. Cisco IOS-XE Copy ip sla 10
 icmp-echo 9.9.9.9 source-interface Vlan10
 frequency 5
ip sla schedule 10 life forever start-time now
track 10 ip sla 10 reachability
ip route 0.0.0.0 0.0.0.0 10.20.255.1 track 10 name Internet-via-firewall
ip route 10.0.0.0 255.0.0.0 10.20.254.2 name corporate-supernet-via-SD-WAN Why The firewall is deliberately outside the routing protocol, so a static naming it is the only way it enters the path - nothing else in the design can advertise a route to a device the IGP cannot see. And a tracked default is not the same as a floating one: an untracked backup only takes over when the local interface goes down, which is no help at all when the firewall is up, the link is up, and the path beyond it is gone. Note Two findings sound alike and are not. static route … points at X, which is on no connected subnet is this step: the next hop is not reachable on any interface, usually because the transit link has not been addressed yet. default gateway … is not inside any subnet configured on this device is the Mgmt tab's out-of-band gateway, and has nothing to do with your routing table. Tracking renders on Catalyst switches, the routers and the Nexus 3548/3550. Nexus fabric switches, Arista, Nokia SR Linux and SR OS, ArubaOS-CX, PAN-OS and the SD-WAN appliances render the route without it, and the generator warns that the failover would not exist on the device, rather than inventing syntax nobody can paste. Complete reference: Cisco IOS-XE Configuration Guides Cisco Nexus 9000 NX-OS Configuration Guides Cisco Catalyst 9000 Configuration Guides 

## Step 5 - Reach the other offices # The office now has gateways and a way out. What it has not got is a path to the rest of the estate, and the firewall is not it. Two shapes, and which one you have was largely decided when the site was built. 

## Static toward the WAN edge # The supernet route from step 4 is the whole design: everything corporate goes to the appliance, the overlay carries it, and the appliance holds a route back to the site block. It needs no protocol and nothing to watch. It also means every new site is an edit on this core. 

## eBGP between the core and the SD-WAN appliance # Where to find it Canvas → Blueprint → Routing → Site edge peering → Core ↔ WAN edge Choose eBGP instead of Static routes , with the site's Local AS and the appliance's Appliance AS . Both halves are generated: the core opens a session to the appliance with BFD and advertises the site block; the appliance advertises what the overlay knows, including the default route at a site that backhauls its Internet traffic. Remote sites are learned, so office thirty-one is not an edit on thirty cores. Cisco IOS-XE Copy router bgp 65001
 bgp router-id 10.20.255.11
 bgp log-neighbor-changes
 neighbor 10.20.254.2 remote-as 65010
 neighbor 10.20.254.2 description SD-WAN edge
 neighbor 10.20.254.2 fall-over bfd
 !
 address-family ipv4
 neighbor 10.20.254.2 activate
 redistribute connected
 network 10.20.0.0 mask 255.255.0.0
 exit-address-family The appliance half is not CLI - an SD-WAN appliance generates a bootstrap document for its orchestrator, and the session appears there as a peer with its local ASN, its router id and the advertise-default switch. You can read and edit it in the appliance's L3 tab, which offers exactly the fields that bootstrap carries and nothing else. Important This one is a first-run decision. Once any site in a plan has generated, the wizard becomes additive: it will still add sites, address them and generate them, but the WAN architecture, the peering mode, the ASNs, the interior protocol and the vendor kits are frozen and their steps are not shown. Switching an existing office from statics to eBGP afterwards is a hand edit on each core and each appliance. Note This is a LAN-side session between the core and the appliance, not a change to how the overlay carries traffic between sites - the overlay still owns that. The shipped Enterprise WAN designs use the static shape, and their spokes carry no routing section by design. Why One router bgp stanza is all a switch has, so a core can hold the interior mesh and this session at the same time - neighbours in two different autonomous systems under one process. What the session buys is that the statics it replaces stop existing: a learned default and a written one side by side would share the load between the firewall and the overlay, which is not a failover, it is half your Internet traffic bypassing inspection. Complete reference: Cisco IOS-XE Configuration Guides HPE Aruba EdgeConnect SD-WAN (Silver Peak) Documentation 

## Step 6 - Validate, then read what generated # Where to find it Canvas toolbar → Validate → - then - → Publish → Generate Static Config → Generate Validate first: Generate stays unavailable while any error is open. Findings group by rule, so seven copies of one mistake read as one row with a count rather than seven problems. The drawer sits beside the canvas, and Locate on a finding rings the device or link it names. The ones this recipe tends to produce: VLAN not defined Step 1 against step 3 - an SVI or a port whose VLAN is in neither the switch’s list nor the project VLAN database. next-hop off subnet Step 4 written before the transit link was addressed. subnet overlap Two sites reusing a VLAN id and auto-assigned as one group (step 3). BGP incomplete Step 5 with a local AS or a peer address still empty - the session would never establish. Important Validate and Generate are two different pipelines. Validate checks the design; the Config tab and the Generate drawer render the templates and report what the template found - the routed-access-switch warning, a tracked route on a platform with no probe, a first-hop gateway the platform cannot express. A clean Validate is not a promise that every device rendered what you typed, so read one generated config per role before you call it done. What each layer checks, and what the bundle contains: Validation & generation . 

## What this recipe does not cover # 
- The management plane - out-of-band addressing, users, AAA, banners: Management and Out-of-band . 
- The firewall's own policy - zones, NAT and rules are designed in Firewall Studio , and a rule change can be simulated against real flows before you make it: what-if . 
- Monitoring - SNMP, syslog and SPAN: Monitoring . 
- More than one site - site tabs, the Overview canvas and per-site exports: Multi-canvas designs . 
- The handover pack - the high-level design, cabling schedule, bill of materials and the automation bundle: Publish . It ends where the platform ends: a configuration per device that you can read, copy and download, with every finding that stood between the drawing and the file already reported.
